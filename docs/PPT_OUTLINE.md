## 第 2 页｜背景与痛点：告警看不完，模型也不敢直接放

**页面标题**：传统 SOC 的告警疲劳，与大模型接入的三重风险

**核心要点**：

- **传统 SOC 的困境**：告警量大、重复率高、L1 长期做机械分诊，真正高危的告警反而容易被淹没。
- **直接接入大模型的三重风险**：
  - **幻觉**：编造不存在的证据或结论；
  - **高并发/高延迟**：告警突发时把模型和 workflow 打满；
  - **动作失控**：模型直接建议或触发封 IP、隔离主机等破坏性动作。
- **设计目标**：自动分诊 + 有界推理 + 人工兜底 + 全链路审计。
- **判断标准**：不是“模型多聪明”，而是“模型出错时，系统能不能兜住”。

**建议配图**：

- 左侧：告警漏斗图（1000 条告警 → 200 条需复核 → 20 条高危），突出“人力被低价值告警消耗”。
- 右侧：三张风险卡片，分别写“会编 / 会慢 / 会乱动手”。
- 底部一行结论：**L1 可以自动化，破坏性动作必须留在人手里。**

**Speaker Notes（约 35 秒）**：

> 传统 SOC 不是没人负责，是告警真的看不完。直接把大模型接进来，会有三个问题：它会编、它会慢、它还可能在没人注意的时候“建议”一个危险动作。所以我的目标不是让 AI 替代人，而是让它做有边界的初筛：能自动关掉的误报自动关，拿不准的升级，高危的必须人来批。

## 第 3 页｜系统整体架构：一条异步链路，四个关键取舍

**页面标题**：Wazuh → Bridge → Redis Stream → Consumer → Dify → 审批/审计

**核心要点**：

- **数据流**：Wazuh 或注入脚本 → Bridge `:8000` → Redis Stream `wazuh:alerts` → Consumer → Dify 工作流 → Agent + 两个只读工具 → 审批服务 `:8002` → Trace。
- **为什么用 Redis Stream 解耦**：
  - Bridge 写入后立即返回 `202`，采集端不被 LLM 延迟拖垮；
  - consumer group + PEL 支持进程崩溃后的消息重新认领；
  - 重试 3 次仍失败进入 DLQ，故障不阻塞后续队列；
  - `XPENDING`、`lag`、DLQ 长度就是现成的健康指标。
- **4C4G 资源取舍**：Dify 整栈按约 **3 GB** 做预算，宿主机留约 1 GB；SOC 四个服务用 systemd 管理；Redis 只监听 `127.0.0.1:6379`。
- **审计旁路**：审批与 Trace 独立于 Dify，Dify 故障不会把审计链一起带走。

**建议配图**：

- 直接复用 README 第 2 节的 Mermaid 架构图，导出为 SVG/PNG。
- PPT 里只保留 5 个主节点：Wazuh、Bridge、Redis Stream、Consumer、Dify；tools/approval/trace 放在下方作为支路。
- 右下角加一个小的“内存预算”饼图：Dify 3 GB / 宿主机 1 GB。

**Speaker Notes（约 45 秒）**：

> 这条链路的关键是“异步”：Bridge 把告警丢进 Redis 就返回 202，Dify 慢不慢、挂不挂，都不会把采集端拖死。Consumer 用 consumer group 消费，进程崩了消息还能重新认领；重试三次还失败就进死信队列。4C4G 上 Dify 整栈只给 3 GB，这是被内存逼出来的架构，不是随便画的一条线。

## 第 4 页｜核心设计 1：把 Agent 关进四字段的笼子

**页面标题**：严格约束的 Agent：四字段 Schema + 两个只读工具 + 3 次迭代

**核心要点**：

- **输出只有四个字段**：`decision`、`confidence`、`reason`、`evidence`。
- **硬约束**：Pydantic `extra="forbid"`；`reason` 不超过 50 字；`evidence` 最多 8 条；工具名必须在白名单内。
- **两个只读工具**：
  - `fetch_wazuh_alerts`：查同源 IP、同主机最近告警，判断是否重复；
  - `search_attack_knowledge`：检索 ATT&CK 子集与 IOC，解释行为。
- **最多 3 次迭代**：控延迟、控成本、防工具循环；同时逼模型“先找证据，再下结论”。
- **双校验**：Dify 的“校验与安全收敛”节点一次，Consumer 侧 Pydantic 再校验一次；非法输出降级为 `watch`，不直接放行。
- **破坏性动作**只能通过 `policy` evidence 表达，且必须带 `destructive=true`、`requires_approval=true`。

**建议配图**：

- 左侧放四字段 JSON 代码块（只保留 8–10 行）。
- 右侧放 Dify Agent 节点截图，标注“Function Calling / 两个工具 / 最多 3 次”。
- 下方画一个简单的循环图：Agent → 工具 → 证据 → 裁决，超过 3 次强制收敛。

**Speaker Notes（约 40 秒）**：

> 我不让模型自由写作文，只让它填四个字段：结论、置信度、理由、证据。证据必须来自两个只读工具，最多调三次。这样既控住了延迟和成本，也逼着它“说话要有依据”。输出在 Dify 里校验一次，回到 Consumer 再校验一次，非法就降级成 watch，绝不直接放行。

## 第 5 页｜核心设计 2：人在回路，破坏性动作只建议不执行

**页面标题**：审批单流转与可重建的审计链

**核心要点**：

- **L1 不执行任何破坏性动作**：`block_ip`、`isolate_host` 等只生成建议，审批通过后仍由 L2 执行器复核（L2 为后续工作）。
- **审批单机制**：
  - 生成 `approval_id`；
  - token 单次有效，默认 24 小时过期；
  - 明文 token 只出现在审批链接里，SQLite 只存 `token_hash`；
  - 批准/拒绝回写 `status`、`decided_at`、`decided_by`、`note`。
- **防重放**：同一 token 第二次提交返回 `already_decided`，网页链接和 API 共用同一套状态机。
- **审计表**：`runs`（一次裁决）、`steps`（每次工具调用）、`approvals`（审批记录）；同时追加 JSONL，保证可查询、可追溯。
- **生产开关**：`APPROVAL_EXPOSE_LINKS=false`，审批链接只通过邮件/钉钉下发。

**建议配图**：

- 上半部分：审批时序图（Agent → Dify → approval → 审批人 → Trace）。
- 下半部分：SQLite 三张表的字段截图，或一条 `SELECT` 查询结果。
- 右侧放一张审批页面截图（批准/拒绝按钮），敏感信息打码。

**Speaker Notes（约 40 秒）**：

> 高危告警不会直接封 IP，而是生成一张审批单：批什么、目标是谁、为什么，都写清楚。审批链接单次有效，数据库里只有哈希；批了、拒了、谁批的、什么时候批的，全部落到 trace。L1 只出建议，真正的执行留给 L2。这样即使模型判断错了，也不会自动造成破坏。

## 第 6 页｜实战排雷 1：Dify 1.17 的 SSRF 与 JSON 转义

**页面标题**：从 403 到 422：两个最隐蔽的 Dify 1.17 兼容坑

**核心要点**：

- **坑 1：SSRF 拦截私网**
  - 现象：Dify 调 tools/approval 失败，`ssrf_proxy` 返回 403，Agent 拿不到工具结果。
  - 根因：1.17 默认拒绝私网和 Docker 网段；容器里的 `127.0.0.1` 不是宿主机。
  - 修复：开启 `SSRF_PROXY_ALLOW_PRIVATE_IPS=true`，只在 squid ACL 放行 `172.17.0.0/16`；**不写 `0.0.0.0/0`**。
- **坑 2：Agent 输出 JSON 嵌套破裂**
  - 现象：Dify 显示成功，审批接口却返回 `422 result_json 不符合 L1 Schema`。
  - 根因：Agent 输出是 JSON 文本，嵌进 HTTP body 时引号被多转义一层，`result_json` 变成损坏字符串。
  - 修复：校验节点输出两级 `result_json` / `result_json_escaped`；HTTP body 只保留一个 body item；模板变量不加引号；审批服务用 `model_validate_json()` 解析。
- **排障方法**：看 `ssrf_proxy` 日志 → 打印真实请求体 → 对照 Dify 1.17 源码/限制 → 做最小修复。

**建议配图**：

- 左侧：`ssrf_proxy` 403 日志截图 + squid ACL diff（`172.17.0.0/16` 高亮）。
- 右侧：修复前/修复后的 HTTP body 对比，圈出多转义的 `\"`。
- 底部小字：Dify 1.17 `_require_single_body_item` 的源码片段（只截 3–4 行）。

**Speaker Notes（约 55 秒）**：

> 第一个坑是 SSRF。工作流一直调不通工具，表面看像网络问题，我先查了容器连通性，最后在 ssrf_proxy 日志里看到 403——Dify 1.17 默认不允许访问私网和 Docker 网段。对照它的 SSRF 配置和 squid 模板后，我没有直接把整个私网放开，而是只在 squid 里加了 172.17.0.0/16 这一段。第二个坑更隐蔽：Dify 显示成功，审批却 422。把真实请求体打出来，发现 result_json 被转义了两层，引号全乱了。最后按 1.17 的单 body item 限制，用两级 dumps 生成 result_json_escaped，模板里不加引号，才把这段 JSON 安全塞进去。

> **答辩提示**：这一页不要念报错，讲“我怎么从现象定位到根因”，老师更看重过程。

## 第 7 页｜实战排雷 2：一个字符串引发的“双审批单”

**页面标题**：`approval.body` 是字符串：审批去重与变量解析

**核心要点**：

- **现象**：一条 `escalate` 告警生成两条审批单；批准其中一条后，另一条一直挂在 `pending`。
- **根因链**：
  - Dify 1.17 的 `http-request` 节点把响应体放在字符串字段 `approval.body`；
  - 结束节点按对象字段取 `approval_id`，拿到空值；
  - Consumer 看到“需要审批但没有审批号”，触发兜底逻辑再建一条。
- **修复**：
  - 新增 `approval_parse` code 节点：`json.loads(approval_body)`，提取 `approval_id`；
  - 结束节点只认 `approval_parse.approval_id`；
  - Consumer 仅在 `approval_id` 为空时兜底。
- **结果**：批次 `6e4fab24` 中两条 `escalate` 各只生成 1 条审批单，无重复、无悬挂。
- **经验**：跨系统边界先“解析成对象”，再谈业务逻辑。

**建议配图**：

- 左侧：修复前“2 条审批单” vs 修复后“1 条审批单”的对比截图（SQLite 查询结果）。
- 右侧：Dify DSL 中 `approval_parse` 节点的截图 + 5 行核心代码。
- 底部画一条简单的因果链：字符串 body → 空 approval_id → Consumer 兜底 → 双审批。

**Speaker Notes（约 55 秒）**：

> 这个 Bug 最像幽灵：Dify 那边明明建了单，但输出里 approval_id 是空的；Consumer 以为没建，又补了一张，于是一条告警两张单。我先排除了 Dify 重试，最后把 approval.body 原样打出来，发现它不是一个对象，而是字符串。于是加了一个 approval_parse 代码节点，先 json.loads，再把 approval_id 传给结束节点。修复后两条 escalate 各只有一条审批单。这个坑让我记住：跨系统边界，先解析，再谈业务。

> **答辩提示**：强调“我不是猜的，是把响应体打出来才定位到的”，这句话很加分。

## 第 9 页｜安全边界与 4C4G 性能取舍

**页面标题**：端口隔离、Token 边界与 3 GB 内存预算

**核心要点**：

- **端口隔离**：`6379`（Redis）、`8001`（tools）、`8002`（approval）不对公网开放；UFW 保留现有规则，安全组只放行 SSH 和必要 Web 端口；Dify 使用 `8081/8443`，按需放行或走 SSH 隧道。
- **Token 边界**：Bridge、tools、approval 使用独立 Token；审批 token 单次有效、只存哈希；生产关闭审批链接回显。
- **4C4G 内存预算**：
  - Dify 整栈约 3.0 GB：api 700m、worker 512m、db 384m、Weaviate 512m、plugin_daemon 256m 等；
  - `mem_limit = memswap_limit`，不允许容器用 swap 超卖；
  - 宿主机留约 1 GB；实测 used 2.4 Gi、available 1.2 Gi、swap 427 Mi，未发生 OOM。
- **可观测性**：`XPENDING` / `lag` / DLQ 长度 / `runs.latency_ms` 四个指标就能判断链路是否健康。

**建议配图**：

- 左侧：网络拓扑图，用红色锁标出 6379/8001/8002 “不对外”。
- 右侧：内存条形图（Dify 3 GB / 宿主机 1 GB），下方放 swap 使用量。
- 角落放一张 `free -h` 或 `docker stats` 截图，关键数字高亮。

**Speaker Notes（约 35 秒）**：

> 安全上我守住一条线：队列和工具服务绝不公网，Redis 只监听本机。性能上不是堆机器，而是给 Dify 整栈做 3 GB 预算，按服务切 mem_limit，容器不允许拿 swap 超卖；宿主机留 1 GB，swap 实测用了 427 Mi，只是兜底，没有 OOM。

## 第 10 页｜总结与展望：把不可控的模型，变成可运维的系统

**页面标题**：已完成的工作、边界与下一步

**核心要点**：

- **已完成**：
  - 异步告警链路：Bridge → Redis Stream → Consumer → Dify；
  - 有界 Agent：四字段 Schema、两个只读工具、最多 3 次迭代；

## 附：预设问答（备用，不占 PPT 页数）

### Q1：你这不就是把现成工具拼在一起吗？

**回答要点**：

- 组件是现成的，但“让它们在资源受限、版本快速迭代的环境里稳定协作”是工程问题。
- 我做了三件不属于“装软件”的事：异步解耦与失败隔离、LLM 输出约束与安全边界、跨版本兼容排障。
- 如果只是拼起来，Dify 升级到 1.17 时系统会直接不可用；我能定位到 SSRF、JSON 转义和审批去重，并做最小修复。

### Q2：为什么用 Redis Stream，不用 Kafka？

- 4C4G 资源受限，Redis 已经在栈内，运维成本最低。
- Stream 的 consumer group、PEL、DLQ 足够覆盖当前量级。
- 如果未来吞吐上来，再把队列抽象换掉，业务层不需要重写。

### Q3：大模型幻觉怎么办？

- 四字段 Schema + 只读工具 + evidence 强制 + 双校验；
- 非法输出降级为 `watch`，不直接放行；
- 破坏性动作必须人工审批，模型判断错了也不会自动执行。
- 不能保证 100% 不幻觉，但能保证“错了不自动动手”。

### Q4：告警文本里如果有恶意指令（Prompt Injection）怎么办？

- 告警文本作为数据输入，不拼接系统指令；
- 工具只读、参数白名单；
- 输出受 Schema 限制，高危动作走人工；
- 当前还没做完整的输入清洗，这是下一步工作。

### Q5：为什么审批 token 只存哈希？

- 防止数据库泄露后被直接重放；
- token 单次有效、带过期时间；
- 明文只出现在审批链接中，服务端只保存 SHA-256 哈希。

### Q6：性能数据是多少？

- 队列：`pending=0`、`lag=0`、`entries-read=27`；
- 端到端延迟：`[端到端延迟]`（答辩前用 `runs.latency_ms` 回填）；
- 资源：4C4G，Dify 整栈约 3 GB，实测 used 2.4 Gi / available 1.2 Gi / swap 427 Mi。

## 附：PPT 制作规范

- **比例**：16:9；标题 32–40 pt，正文 20–24 pt，代码 14–16 pt。
- **配色**：深蓝/石墨灰为主，青色作强调，橙色只标“风险/待办”；不要大面积红绿。
- **每页一个结论**：标题就是结论，正文只放支撑证据。
- **代码只截关键行**：一页不超过 10 行；完整代码放附录或备份页。
- **日志要裁剪**：只保留报错关键行，圈出 403 / 422 / approval_id 等关键词。
- **截图打码**：服务器 IP、API Key、邮箱、Token 一律替换为 `<YOUR_IP>` / `<YOUR_API_KEY>` 或马赛克。
- **动画**：少用或不用；第 6、7 页可以用“问题 → 证据 → 修复 → 结果”四步逐步出现。
- **备份页**：建议在正式 10 页后加 3 页备份：完整架构图、SQLite 表结构、Dify DSL 关键节点截图，方便答问时翻。
